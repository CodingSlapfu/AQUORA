## Verified architectural observations

1. **Small RAM bands, not a full framebuffer.** SLOOP's `vis_draw` draws a 240×240 image in **two 240×120 passes** via `cv_begin`/band y clipping/`cv_blit`, calling the visual renderer in each pass. AQUORA `device/ui.c::draw` currently renders **five 240×48 bands**. Try 2×120, 3×80 or better scratch tiling only **if RAM allocation and BSP canvas contract safely permit**. Larger bands reduce repeated per-band dispatch and LCD command/window overhead, but may consume scarce SRAM and expose longer audio latency; benchmark full device mix/working memory, never change blindly.
2. **Overlap LCD DMA with CPU work.** SLOOP `lcd_data` starts a RAM-backed DMA and keeps `lcd_busy`; `lcd_sync` waits only before another LCD operation/buffer overwrite. Its source comments explicitly allow the final strip transfer to continue while the main loop works. Audit AQUORA's actual fm1-base/felucca-bsp `cv_blit`/SPI/DMA implementations and whether `app_frame` or `draw` unnecessarily synchronizes after every small strip. Consider safe double buffering / last-strip async completion where ownership and memory lifetime are proven. Confirm any optimization does not corrupt pixels or miss audio deadlines.
3. **Audio statistics/snapshot, no FFT in ISR.** SLOOP `vis_update` snapshots 512 samples of a display scope ring from the audio path and a short meter/note-hit state; FFT and style dynamics run **outside audio ISR**, only on the visualizer. AQUORA already captures scope/peak data and has a geometry worker; verify there is no duplicated capture, FFT or waveform accumulation in hidden or non-animated pages, no unsafe IRQ lock across large copies, and input snapshot ownership remains correct.
4. **UI cache/dirty updates.** SLOOP's UI caches previously drawn portions and redraws changed regions; its full-screen visualizer runs on alternate UI calls (`ui.frame & 1`) while ordinary parameter UI stays lazy. AQUORA already gates `dirty` and band visibility; inspect whether the current PLAY/fullscreen path renders static typography, backgrounds, battery, graph overlays repeatedly where caching or a stable backing layer could avoid redundant work **without losing visual detail**.
5. **Integer motion and lookup tables.** SLOOP stores small animation state and uses Q15 sine lookup for orbit, waves and meters. AQUORA already uses a sine LUT and core-1 geometry path; profile actual costs before converting more arithmetic. Do not drop color depth, particle density or effect variety based on unmeasured guess.
6. **SPI-bus physics matter.** SLOOP's `lcd.c` defines default `LCD_BAUD=4` (peripheral clock/5: approximately 12 MHz with stock 60-MHz peripheral clock), though build overrides and observed conditions may differ. At **12 MHz raw**, an entire 240×240 RGB565 frame (**115,200 bytes**) takes a theoretical **76.8 ms on wire**, or just 13.0 FPS maximum before commands/CPU. That **does NOT establish SLOOP reaches 20 FPS**. AQUORA's actual baud/throughput is not established here; measure or inspect its pinned BSP and hardware clock. For 20 full RGB565 frames/s, payload alone requires 2.304 MB/s (~18.432 Mbit/s), so effective SPI throughput must exceed this.
7. **SLOOP skips some UI-frame rendering deliberately.** Its visualizer draws only every other `ui_draw` call, not every main-loop tick. This is a resource policy, not proof of delivered 20 FPS. AQUORA's requested target and visual richness remain independent.

## AQUORA owner evidence and source defect

Physical AQUORA 0.6.5 photos: `AUTO (20 target)` displays `PLAY BLITS FPS×10 = 89` (**8.9 FPS**) and `MISSED/2s=18`; user states manual `20 FPS` yields `PLAY BLITS FPS×10 = 94` (**9.4 FPS**). Callback mean 5,081 us, peak 5,265 us, P95/P99 5,300 us, 256-frame deadline 5,805 us; audio mean 4,828 us, FX mean 280 us, audio+FX budget 87%, 16 active voices, DMA XRUN delta **0**, input drops 0, worker fallback 0. Diagnosis in `device/app.c`: `fps_auto` selects displayed text/storage but currently does not control throttle selection; a P95 of 5,300 forces a 100-ms (~10-FPS) interval in BOTH modes. `UI DRAW us = 57,907` was seen on a **diagnostics page**: do not treat it as measured PLAY render/transfer cost. PLAY FPS is latched from PLAY intervals, so measure directly under PLAY/fullscreen conditions.

## Focused next-build acceptance/experiments (not automatic changes)

1. Profile physical PLAY/fullscreen **per-stage** timing: clear/background/static UI, reactive geometry, band rasterization, LCD command setup, DMA transfer/wait, core-1 mailboxes, audio callback mean/p95/p99/max and XRUN. Record display page/visualizer/boot clock/SPI setting, RAM and 1-core fallback. Separate CPU time from SPI transfer time. Compare with static diagnostic page.
2. Verify fixed `20 FPS` vs `AUTO` semantics; make setting truthful and safe. Do not force more work into audio ISR or remove XRUN safety. If audio can only sustain ~10 FPS with existing DSP load, expose honest status and optimize measured hotspots rather than mislabel achieved FPS.
3. A/B existing 5×48 canvas vs permitted larger band/double-buffer/async strategies, then cache unchanged UI or skip hidden work. Preserve exact Original visualizer identity and required water/sand Visualizer 2 redesign (#17), no visual downgrade. Measure motion quality and display corruption/tearing on hardware and emulator.
4. Preserve current physical zero-XRUN/no-input-drop snapshot as a regression baseline, but require longer audio + visual concurrent device testing and fallback tests before asserting stability.
5. Keep original AQUORA work independent. SLOOP code is **GPL-3.0-only**; do not transplant SLOOP visualizer source, assets or LCD driver into AQUORA without a verified code-specific license/distribution review. Reimplement tested concepts through AQUORA's own platform APIs.

**Conclusion:** SLOOP validates several low-level ideas, notably small canvases, async display DMA, explicit audio/visual separation and lazy UI; **it does not demonstrate a drop-in FPS win**. The highest-value unknown is what fraction of AQUORA's ~9 FPS is due to **intentional P95 throttling versus LCD transfer/rasterization cost**. Benchmark first.
