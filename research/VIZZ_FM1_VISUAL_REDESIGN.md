# Vizz.fm inspiration → AQUORA FM-1 visual direction (2026-11-04)

Owner feedback after installing released AQUORA 0.5.0: music sounds good and runs great overall; possible intermittent crackling under processing load; PERFORMANCE is missing readily readable live CPU, Audio Processing and FX Processing; current replacement Water Cymatics visualizer is aesthetically rejected; too many instrument features/settings remain difficult or impossible to locate. This document is **research and next-build design requirements, not implementation**. Preserve published 0.5.0 and rollback.

## Source research
- https://vizz.fm/ and https://vizz.fm/visualizers/ : Vizz.fm advertises 11 scene engines, 70+ built-in presets and per-scene colors, speed, intensity, geometry, camera and sensitivity; bass/mid/treble-reactive bindings and stackable effects. Its gallery includes Mesh Grid, Wavy Form, Particle Dance, Polar Curves, Audio Tunnel, Equalizer Rings, Dot Grid, Frequency Hallway, etc.
- https://discourse.threejs.org/t/vizz-a-free-music-visualizer-in-your-browser/91484 : author's description says audio uses Web Audio API/AnalyserNode configurable FFT, WebGL/Three.js rendering, postprocessing, frame-rate-independent movement and saved presets.
- Browser visuals have GPU and far more RAM/graphics throughput; cannot port Three.js, GPU shaders, WebGL bloom, 70 presets or thousands of particles wholesale to an FM-1 240x240 LCD and JieLi AC791N. **Inspiration is design language and reactive mapping, not code reuse.** Do not scrape/copy artwork, shaders, brand assets or site source.

## New proposed visualizer direction — Vizz-inspired, not Water Cymatics
- Current 0.5.0 `device/visual_worker.c::cymatics_job` computes 8 rows x 25 points of side-view waves. Owner rejects the style, so do not simply enhance wave ripples or add a new layer of water effects. Replace the second-visualizer direction with visually striking **black-background, luminous, smooth 2.5D music-reactive geometry**, easy to read on 240x240. Keep original visualization selectable; treat current water effect as obsolete rather than forcing it as flagship.
- Prefer **one common efficient rendering core** with a small, distinct set of Vizz-inspired looks: (a) **Mesh Flow**: perspective-tilted wireframe terrain folds/rises with bass and chord harmonics; (b) **Wave Ribbons**: two/three flowing luminous waveform ribbons responsive to melody/pads/choir; (c) **retired polar-curve concept**: flower-like rotating polar curves/points energized by note, drums and phrase transitions. These are names/concepts for custom original implementation, not literal Vizz scenes. Only include modes actually measured sustainable on the device; don't multiply CPU costs by maintaining multiple renderer architectures. Simpler single flagship first if performance demands. User should get an immediate visible difference on mode change.
- Map *existing* engine telemetry directly to visuals at **control rate**: bass envelopes -> broad slow deformation/scale; drum onsets/accents -> quick pulses/shocks; piano/lead notes -> line/wave tracing; pads/choir -> layered color and gentle drift; current intention, harmonic/key state and exact Hz -> palettes and distinctive geometric modes; FX and arrangement events -> restrained particles/halos. Use smoothed bounded dynamics with stable motion, not a generic audio master meter or a static rotating logo. Avoid heavy FFT; no graphics/draw in audio interrupt. A small optional spectrum if really desired only with proven safe off-audio-thread calculation.
- Real on-device controls in an easy **PLAY > VISUALS** shortcut and **SETUP > VISUALS** overview: Look, Color Palette, Sensitivity, Energy/Intensity, Speed, Depth/Tilt, and optional Reactive Mapping (Bass/Melody/Drums/All). A few context-sensitive K1–K4 knobs per tab; all named and observable, no scattered hidden groups. Include easily chosen factory presets (e.g., Tranquil, Ethereal, Radiant, Cosmic), persistent settings in user preferences/banks as appropriate and safe defaults. No unsupported software-adjustable camera geometry without visual effect.
- Keep 240x240 dominant/full-screen PLAY canvas; small transient control overlay when knobs move and unambiguous mode labels. Use precomputed sine/color tables, fixed max vertex count/particles, low-res mesh projection, scanline partial updates and dirty rectangles, optional core-1 with guarded fallback, and no dynamic allocation or blocking worker waits in audio. Test core-1 OFF as well. Avoid costly full-frame gradients, raster bloom, per-pixel shader emulation, or depth passes.
- **Acceptance:** 20 or more **actual LCD-delivered fresh frames/s** sustained (at least 60s and representative longer listening) for each visual look with 16 voices and music+FX; compare geometry, DMA callbacks, xruns, LCD bandwidth, p95/p99, memory and UI response. Host frame submissions are NOT LCD delivered FPS. Do not claim physical pass before owner hardware test. Do not sacrifice sound stability; leave unsatisfied physical targets open explicitly.

## New performance screen requirement (crackling feedback)
- Hardware crackling is **suspected, not confirmed** as CPU/FX underrun cause. Record conditions; isolate FX, instruments, Nature, drums, voice count and both visualizers. Compare actual DMA XRUN **delta per 1s/5s**, callback mean/p95/p99/peak, per-core activity, FX bypass, long renders. Distinguish real clipping from DMA xruns, limiter pumping and interrupted writes. Preserve the loved 0.5.0 music balance.
- `device/ui.c::performance()` currently shows PLAY BLITS FPS, missed slots, audio/FX P95/PEAK and **combined** AUDIO+FX budget percent, plus XRUN delta; **it does not give the requested LIVE CPU% and separate AUDIO PROCESSING% and EFFECT PROCESSING% on one immediately understandable screen.** Add a clean PERFORMANCE dashboard with at least:
  - **CPU LOAD (%)**: Core 0 and Core 1 where reliable supported, or a clearly labeled measured/estimated combined CPU %. Never label callback DSP % as whole CPU usage.
  - **AUDIO (%)**: mean and peak/p95 compute time as % of real 256-frame ~5805µs deadline (excludes separately timed FX; avoid double count).
  - **FX (%)**: independent mean and peak/p95 DSP FX time as % of same budget; **TOTAL (%)** = AUDIO + FX where measurement definitions match; highlight near deadline.
  - **XRUN**: cumulative and last-interval increment, plus active voices, **true measured fresh LCD FPS**, frame misses and optional core-1 fallback.
- Update measurements live ~1 Hz or faster if safe, with prominent readable large numbers/bars, perhaps tiny low-cost rolling trends. Keep display lightweight and responsive; actual counters use existing instrumented timers and one UI-rate snapshot. Use explicit metric definitions. If CPU busy/idle info unavailable, implement/calibrate a safe device-side idle-time estimator and label it as estimate; never invent %. Move verbose diagnostic details to one accessible secondary tab.

## Whole instrument discoverability/ergonomics
- Re-audit ALL actual firmware features and controls against current UI/Docs: Play Along vs Change Key, frequency Auto/Manual/Reference/Lock, 432/440, per-role patches and locks, New Song vs Reroll Sounds, Nature Beds, binaural stereo settings, Sacred Bass, Glide/Vibrato, sound editing (DEMAKE-inspired waveform editor in separate queue), all DRUMS, all MIX, Master FX, voice inspector/source isolate, 16/32/64 loops, saved 4 banks, LEDs, graphics and FPS.
- Current `device/ui.c` has six top-level pages and STILL retains many legacy `groups[]`, so verify routing and discoverability by **walking every control on the device/emulator**, not assuming category names make features reachable. Add a user-facing **SETTINGS DIRECTORY / QUICK FIND** that presents human-readable categories and lets SELECT choose, EDIT open, HOME back, with 1–3 obvious actions to common settings and direct ARP/GLO shortcuts. Every actual parameter must be editable from at least one visible, labeled destination, including reference tone/currency and visualizer options; avoid unadvertised hidden gestures and inert K1–K4 fields.
- Make a concise correct 0.5+/next-version manual / on-device hints. Do not reuse stale version 0.3.0 manual page. Use a navigation matrix and host automated path tests for EVERY setting, plus physical FM-1 owner usability review.
